title: Cluster benchmarks
---

Real numbers from a live LAN fleet running the `v0.34.4-cluster.1` release
build — no simulation, no synthetic harness. Every model was already on the
head node's disk; each cell below is one real `/api/generate` request against
`ollama serve` with `OLLAMA_CLUSTER=1`.

## Fleet

| Node | Role | GPU |
|---|---|---|
| Head (Linux) | head | NVIDIA RTX A4500, 20 GB |
| Mac peer | RPC worker | Apple M2 Max, ~25 GB free (unified memory) |
| Mac peer¹ | RPC worker | Apple M1 Air, ~9 GB free (unified memory) |

Other machines were on the LAN and discovered fine, but didn't have enough
free VRAM to take part in any of these runs. Peers were found over UDP
discovery with zero manual wiring — just `OLLAMA_CLUSTER=1` on each machine,
no `--rpc` flags or static peer list.

¹ Only used for `deepseek-r1:70b` (see the table below): at 39.6 GB it needed
this second Mac RPC peer alongside the M2 Max to have enough combined free
memory to run at all, so that row is the only one in the table below that
used a three-machine fleet instead of two. Every other model ran on just the
head and the M2 Max.

fell back to CPU) — half the RPC hops per token, and that trade won
decisively. At 32K and 128K, larger KV cache pressure leaves neither
algorithm room to choose differently — both converge on the same two-peer,
81-layer split and near-identical throughput.

## Takeaways

- **69 requests attempted, all 69 eventually succeeded** (one greedy/4K
  cell needed one retry after a transient HTTP 500 — see the footnote above;
  `deepseek-r1:70b` contributes 6 of the 69 but has no CPU-only leg, since
  that baseline is impossible for it — see footnote ⁴).
- **Best observed speedup: 8.6×** (`granite4.2:30b`, 32K context, greedy)
  over the same model's CPU-only baseline on the same machine.
- Models in the 18–25 GB range that don't fit the head's 20 GB card benefit
  the most — they're CPU-bound (2–4 tok/s) without cluster mode and
  GPU-speed (15–70 tok/s) with it.
- **Correction**: an earlier version of this table set `rpc_placement` as a
  top-level JSON field instead of nesting it inside `options`, where the API
  actually expects it (see `api.Runner` in `api/types.go`, and "Per-request
  overrides" in `cluster.mdx`) — silently ignored, no error, so every
  request used the server's default env policy regardless of which mode was
  requested. All 48 waterfill/greedy cells above (24 rows × 2 strategies)
  were rerun with the fix, so they're now a real comparison.
- **Greedy wins more often than waterfill**, but not always: greedy is ahead
  in 18 of 24 rows (one row, `deepseek-r1:70b` at 32K, ties), usually by
  using one peer instead of two and saving the extra RPC hop per token —
  including `deepseek-r1:70b` at 4K, its clearest case (footnote ⁴). Waterfill
  wins when spreading layers across both peers adds more raw compute than the
  hop costs (`qwen3-coder:30b` at 32K: 60.24 vs 49.91) or when greedy's
  narrower split hits a KV-cache wall that waterfill's wider one doesn't
  (`granite4.2:30b` at 128K, footnote ³). Neither strategy is a safe default
  across this whole model set. The [placement study](#placement-study-october-2026)
  below found that the gap is mostly the slowest member of the peer list, and
  replaces the free-memory split with a local-first fill.

## Known exception: `qwen3.8:27b`

`qwen3.8:27b` was tested the same way (CPU-only / waterfill / greedy × 4K /
32K / 128K) and is deliberately left out of the table above — its numbers
would misleadingly read as "cluster barely helps":

| Context | CPU only | Waterfill | Greedy |
|---|---|---|---|
| 4K | 2.57 | 2.95 | 3.11 |
| 32K | 2.89 | 2.87 | 2.88 |
| 128K | OOM⁵ | 1.93 (265.8s load) | 1.54 |

These runs logged 0/66 layers offloaded on every configuration. An earlier
version of this page blamed missing CUDA/RPC support for the model's hybrid
SSM/attention architecture. That does not hold up: **single-box check** (one
20 GB RTX A4500 Linux box, no cluster, 160 generated tokens, median of two
runs) shows `qwen3.8:27b` offloading normally, and the real slowdown there
was an Ollama-side launch setting:

| Build | Layers on GPU | Default sampling | `temperature: 0` |
|---|---|---|---|
| Before (fit target padded for the vision projector) | 59/66 | 13.5 tok/s | 14.9 tok/s |
| After (llama-server's own fit target) | 63/66 | 18.5 tok/s | 21.6 tok/s |

llama-server's fit step already reserves the projector's memory, and Ollama
added the projector size plus 1 GiB to `LLAMA_ARG_FIT_TARGET` on top of that,
so fewer layers were placed on the GPU. Sampling settings matter much less
(about 5-10%: speculative-draft acceptance is lower at non-zero temperature).
Why the cluster runs above showed 0/66 is not established; they were not
repeated after this fix, so treat the table as unexplained rather than as an
architecture limit.

⁵ The 128K CPU-only run hit an out-of-memory error allocating an 888 MB
vision-encoder buffer. The head had ~20 GB of RAM available at the time, so
this reads as transient allocation pressure/fragmentation under a large
(131072-token) context rather than a hard resource wall — not chased
further.

## Placement study, October 2026

Everything above compares `greedy` and `waterfill` with one run per cell. This
section measures what actually decides the result: which devices hold weights,
and how many. It answers
[#11](https://github.com/borism/ollama-cluster/issues/11) (why greedy usually
beats waterfill) and
[#66](https://github.com/borism/ollama-cluster/issues/66) (the default split
ignores device speed).

### Setup

| Node | Role | Device |
|---|---|---|
| Head (Linux) | head | NVIDIA RTX A4500, 20 GB (17.7 GB free) |
| M2 Max Mac | peer | Metal, 32 GB unified (26.8 GB reported) |
| MacBook Air | peer | Metal, 16 GB unified (12.7 GB reported) |
| Intel MacBook Pro | peer, other subnet, pinned by `rpc_servers` | Vulkan on an AMD Radeon Pro, 8 GB |

`0.40.11-cluster.1`, RPC protocol 8.0.1, the Macs about 0.5 Gbit/s and 0.7 ms from the head.
To get models that overflow the A4500 by more than a few GiB, three q8_0 builds
were pulled from the registry (`qwen3.8:27b-q8_0`, `gemma4:31b-it-q8_0`,
`nemotron-3.5-lightning:30b-a3b-q8_0`, 99 GB).
The head ran with `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q4_0`.
Every cell is one model load, one discarded warm-up request, then three timed
requests per prompt: a 30-token prompt (generation speed) and a 5,200-token
prompt (prompt speed, generation after a long prompt). `temperature` 0, `seed`
42, 128 generated tokens, `num_ctx` 8192 unless a row says otherwise. Peers were
pinned with `rpc_servers` and the split set with `tensor_split` (peers first,
then the local GPU), except the rows marked "auto". The per-device split is read
from llama-server's `load_tensors` / `KV buffer` lines. **±** is the population
standard deviation of the three requests of one load: it does not include
load-to-load variation, which is larger. Loading the same configuration twice
(a pinned "default" cell and an "auto greedy" cell) gave short-prompt generation
speeds within 0-1 % for gemma4 and granite4.2 and flint, and after the 5k
prompt flint differed by 8 % (36.7 vs 39.7). In all: 92 model loads and 411
timed requests; 20 requests failed (see the end).

### How fast is each device, as seen from the head

The whole of `qwen3.5:9b` (Q4_K_M, 6.6 GiB) on one device (`tensor_split "1,0"`
or the local GPU alone), 3 requests each:

| Device | Memory bandwidth (spec) | Generation tok/s | Prompt tok/s (5k) |
|---|---|---|---|
| A4500, local | 640 GB/s | 76.1 ± 0.5 | 2,560 ± 790 (3,117 steady) |
| M2 Max, over RPC | 400 GB/s | 26.3 ± 0.8 | 422 ± 6 |
| MacBook Air, over RPC | 68-100 GB/s | 8.7 ± 0.1 | 105 ± 3 |

Per byte, the M2 Max is 2.9x slower than the local GPU for generation and 7x
for prompt processing, the Air 8x and 29x. The spec-sheet bandwidth ratio
(1.6x for the M2 Max) understates the M2 Max by almost half, because every peer
also costs a roughly constant 20-30 ms per generated token: a 3.3 GB model
(`qwen3.5:4b`) generates at 29 tok/s on the M2 Max, the 7.1 GB model at 27, while
bandwidth alone would predict 2x apart. The Intel MacBook Pro runs
`qwen3.5:4b` at 5.1 ± 0.5 tok/s and about 13 prompt tok/s, slower than the Air,
and with the free-memory default split it was handed 10.2 GiB of
`gemma4:31b-it-qat`: 1.1 tok/s, against 4.4 ± 0.5 when the A4500 took 85 % and
the Intel MacBook Pro 2.5 GiB (and 14.6 with the M2 Max instead).

### Why waterfill loses: the extra device

llama.cpp splits layers in proportion to each device's free memory. Waterfill
lists every usable peer, so the MacBook Air always gets about a fifth of the
weights, and it is the slowest device in the fleet. Greedy stops at the M2 Max.
Same model, same context, only the peer list differs:

| Model | Peers | Weights GiB (A4500 / M2 / Air) | Generation tok/s | Prompt tok/s |
|---|---|---|---|---|
| gemma4:31b-it-qat | M2 (greedy) | 7.2 / 9.2 / - | 14.6 ± 0.2 | 155 ± 11 |
| gemma4:31b-it-qat | M2 + Air (waterfill) | 5.7 / 7.4 / 3.3 | 6.8 ± 0.0 | 67 ± 0 |
| flint:40b-a2b (MoE) | M2 (greedy) | 9.4 / 13.7 / - | 43.8 ± 0.5 | 926 ± 13 |
| flint:40b-a2b (MoE) | M2 + Air (waterfill) | 7.5 / 10.3 / 5.3 | 30.9 ± 0.5 | 362 ± 141 |

Auto-selected `greedy` and `waterfill` and the same lists pinned by hand gave the
same splits and speeds. Adding the Air costs 2.1x on the dense model, 1.4x on
the MoE (a MoE reads few bytes per token, so a slow device hurts less). On
this fleet that is the whole greedy-versus-waterfill gap, and it is not a
property of the algorithms but of what they put on the slowest member.

A split by speed does not fix it, and a split that leaves the Air empty costs
nothing:

| 3 devices, A4500 + M2 Max + Air | gemma4:31b-it-qat | flint:40b-a2b |
|---|---|---|
| default (free memory) | 6.8 ± 0.0 | 31.2 ± 0.2 |
| proportional to measured speed (68 / 24 / 8 % for gemma4, 62 / 30 / 8 % for flint) | 9.4 ± 0.1 | 37.3 ± 1.9 |
| A4500 as full as fits, Air listed but empty | 16.9 ± 0.1 | 53.8 ± 2.1 |
| A4500 as full as fits, M2 Max the rest (Air not listed) | 16.8 ± 0.0 | 52.5 ± 4.3 |

Speed-proportional shares are the wrong shape for a layer split: layers run one
after another for a single request, so time is the sum over devices of
bytes / speed, not the maximum, and the sum is smallest when the fastest device
is filled first. Every peer also adds its fixed per-token cost.

### The split on the A4500 + M2 Max pair

Generation tok/s (after the 5,200-token prompt in brackets) as the A4500's
share of the weights rises. "Default" is llama.cpp's free-memory split (A4500
41-44 %).

| Model | Default | 50 % | 60 % | 75 % | 85-90 % | A4500 alone (rest on CPU) |
|---|---|---|---|---|---|---|
| gemma4:31b-it-qat | 14.6 (12.3) | - | 15.9 (13.7) | 16.4 (15.0) | 16.8 (14.9) | 14.4, then CUDA out of memory on the 5k prompt |
| granite4.2:30b | 19.3 (17.0) | - | 21.4 (18.9) | 21.0 (19.7) | 22.9 (20.1) | 20.3 (17.9) |
| flint:40b-a2b | 44.0 (36.7) | 50.5 (44.2) | 52.5 (50.3), 62 % is the most the A4500 holds | - | - | 19.5 (43.5), experts on CPU, spread 3 and 15 tok/s |

Generation rises with the A4500's share up to what fits, for every model (granite4.2's
60 % and 75 % points are 0.4 tok/s apart the wrong way, inside the noise); the
sweeps never found an interior optimum. Prompt processing moves
more than generation (gemma4: 160 to 359 tok/s, granite4.2: 186 to 496)
because prompt processing sends activations over the network for every layer
that crosses a device boundary and the peers' GPUs are far slower at it.

The shortfall decides how much there is to gain. When the model needs most of
the M2 Max anyway, the default is already close to "fill the GPU":
`nemotron-3.5-lightning:30b-a3b-q8_0` (32.6 GiB) splits 13.6 / 18.6 GiB by
default and 13.6 / 18.6 with the fill, 74.0 vs 73.6 tok/s.

### The fill rule, end to end

`cluster.fillSplit` fills the local GPU (minus a 3 GiB margin for compute
buffers and the CUDA context), then peers largest-free-memory first, and drops
a peer that gets nothing. These are the splits it computes for each model on
this fleet, pinned and run (three requests each, `tensor_split` as computed):

| Model | GiB | Default gen / prompt | `fillSplit` gen / prompt | Local only gen / prompt |
|---|---|---|---|---|
| granite4.2:30b | 16.5 | 19.2 ± 0.1 / 203 | 20.5 ± 0.4 / 398 | 20.3 ± 1.6 / 705 |
| qwen3.6:35b-a3b | 20.2 | 66.8 ± 3.7 / 713 | 73.7 ± 0.7 / 863 | 59.7 ± 4.8 / 606 |
| flint:40b-a2b | 24.2 | 43.8 ± 0.5 / 926 | 61.5 ± 1.8 / 976⁵ | 19.5 ± 3.1 / 294 |
| nemotron-3.5-lightning | 23.7 | 77.8 ± 2.3 / 666 | 76.5 ± 2.8 / 772 | 47.5 ± 0.3 / 344 |
| qwen3.8:27b-q8_0 | 27.1 | 13.2 ± 0.0 / 206 | 13.7 ± 0.0 / 234 | 3.6 ± 0.0 / 226 |
| gemma4:31b-it-q8_0 | 30.4 | 9.8 ± 0.0 / 162 | 9.9 ± 0.1 / 181 | 2.4 ± 0.0 / 143 |
| nemotron-3.5-lightning q8_0 | 32.6 | 74.0 ± 3.8 / 717 | 73.6 ± 3.1 / 711 | 8.1 ± 1.4 / 36 |

⁵ with the 5k prompt, 41.9 ± 1.5 against 39.7 ± 2.3 for the default and 50.3 for the
hand-picked 62 % cell: flint's long-prompt generation varied by 10 tok/s between
loads of near-identical splits. Treat flint's gain as real but of uncertain size.

What this says, and does not:

- The fill never lost to the default beyond noise, and gained 0-40 % generation
  and -1 to +96 % prompt speed on the M2 Max pair. (Seven models: with the
  corrected KV estimate, `gemma4:31b-it-qat` and `qwen3.8:27b` are judged to
  fit the A4500 alone, so the code no longer asks the cluster about them; their
  hand-picked rows are above.) The gain is largest for dense
  models whose weights barely exceed the A4500 and zero when the model is so
  large that both splits come out the same.
- **Models that nearly fit locally were as fast, or faster, on the A4500 alone
  with a few layers on the CPU**: granite4.2 (2 of 65 layers on CPU) generated
  20.3 vs 20.5 and prompt-processed 3.5x faster; qwen3.8:27b (2 of 66) 27-32 vs
  34 and 4x faster. A spill of a few percent is cheaper than a network hop on
  every layer boundary. The cluster only clearly wins from about 10 % of the model
  on the CPU (gemma4 q4: 14.4 vs 16.8; the q8 models: 2-4 vs 10-14). Placement
  still sends the shortfall to peers whenever the estimate does not fit
  locally; a "spill threshold" is a follow-up, with only four models behind it.

### Long context, and how KV cache enters (#11)

**KV is accounted for.** `llm.PredictServerVRAM` adds a KV term
(`2 * layers * kv_heads * head_dim * num_ctx * 2 bytes`), greedy compares the
running total against it, and `--fit` re-checks with real buffers at load time.
The working theory in #11 (greedy does not account for the KV cache) is refuted.
What the estimate got wrong was the 2 bytes: it counted every cache as f16,
whatever `OLLAMA_KV_CACHE_TYPE` said.

`granite4.2:30b` (16.5 GiB, 64 layers, 8 KV heads) on the head with a q4_0 cache,
greedy auto-selection, peers pinned afterwards for the speed:

| `num_ctx` | Estimate (f16 KV) | Real KV (q4_0) | Peers greedy chose | Generation tok/s |
|---|---|---|---|---|
| 4,096 | 17.5 GiB | 0.3 GiB | M2 | 19.1 |
| 32,768 | 24.5 GiB | 2.3 GiB | M2 | 19.3 (12.8 after a 22k-token prompt) |
| 131,072 | 48.5 GiB | 9.0 GiB | **M2 + Air** | the load aborted (the Air's RPC worker was down); M2 alone: 13.3 ± 1.4 |

The list flips exactly where the estimate passes what the A4500 and M2 Max can
hold (17.2 + 25 GiB). With a real 9 GiB cache the model needs 26 GiB and the
two fit with room to spare, so the third device was added for nothing, at a
cost of 1.4-2.1x (see "Why waterfill loses"; the 128K row of the first table,
7.84 tok/s, looks like the same effect). Estimate, real KV and tok/s with the cache type varied and everything
else fixed (granite4.2:30b, A4500 + M2 Max pinned, default split):

| KV cache | `num_ctx` | Real KV | Estimate | Where it ran | Generation tok/s (22k-token prompt) |
|---|---|---|---|---|---|
| f16 | 32,768 | 8.0 GiB | 24.5 GiB | all on GPUs | 20.3 ± 0.0 (15.1 ± 0.5) |
| q8_0 | 32,768 | 4.3 GiB | 24.5 GiB | all on GPUs | 19.5 ± 0.0 (13.1 ± 0.2) |
| q4_0 | 32,768 | 2.3 GiB | 24.5 GiB | all on GPUs | 19.1 ± 0.3 (12.8 ± 0.3) |
| f16 | 131,072 | 32.0 GiB | 48.5 GiB | **13 of 65 layers on CPU** | 7.7 ± 0.0 (5.2 ± 0.2 after 5k) |
| q8_0 | 131,072 | 17.0 GiB | 48.5 GiB | all on GPUs | 18.7 ± 0.0 (16.8 ± 0.2 after 5k) |
| q4_0 | 131,072 | 9.0 GiB | 48.5 GiB | all on GPUs | 13.3 ± 1.4 (15.9 ± 0.5 after 5k) |

So the cliff has two sources, and which one you hit depends on the cache type:
with an f16 cache at 128K the model really needs about 49 GiB, which is more
than the A4500 and the M2 Max together; a third device, or the CPU, is
unavoidable and the run is slow whichever you pick (7.7 tok/s on CPU spill).
With a q8_0 or q4_0 cache it fits and the estimate adds the Air regardless.
Generation speed itself barely depends on the cache type when everything fits
(19.1-20.3 at 32K); quantized caches cost 13-15 % after a very long prompt.
The benchmark above did not record its cache type; both stories fit its 7.84.

`PredictServerVRAM` now scales the KV term by the cache type (f16 2, q8_0 1.0625,
q4_0 0.5625 bytes per element), which removes the spurious Air at 128K for q8_0
and q4_0 caches. Still counted wrongly, not changed here: sliding-window layers,
recurrent (SSM) layers, and `key_length` differing from `embedding / heads`.

One more KV-related check came back clean: `gpt-oss:20b` (12.9 GiB) at 8K, 32K and
131K contexts stayed on the A4500 alone (108.5, 104.9, 108.7 tok/s); the estimate
did not make it spill for no reason.

At 128K the fill also helps: A4500 50 % (hand-picked) gave 19.9 ± 0.2 against
13.3 ± 1.4 for the default (+50 %), and the computed split 20.5 ± 0.2
(18.4 with a 5k prompt). With a 22k-token prompt at 32K context,
granite4.2 generates 15.7 ± 0.0 with the fill against 12.8 ± 0.3 by default,
and processes the prompt at 278 against 149 tok/s.

### Recommendation

1. **Fill local-first, peers by free memory, only as many peers as needed**
   (`cluster.fillSplit`, now the default when the host has one GPU). It is
   never worse than the default beyond noise on the seven models it applies
   to, it removes the 1.4-2.1x loss from an unneeded slow peer, and it needs no
   per-device speed number. The rank "largest free memory first" was right
   for every pair tested here (A4500 before M2 Max before Air before the
   Intel MacBook Pro's 8 GB card); a table of memory bandwidth per device name
   would only matter when a small fast peer sits next to a big slow one.
2. **A measured speed signal is not needed for this decision.** A bandwidth
   table mis-predicts the M2 Max by 1.7x because of the fixed per-peer cost;
   a bench on join would capture it (the `qwen3.5:4b` probe above takes under
   a minute per peer), but the ranking was already right without either.
   Worth adding later for deciding whether a peer is worth using at all
   (the "spill threshold" above), not for splitting.
3. **Fallback:** llama.cpp's own split (memory-proportional with `--fit`)
   whenever the layout is not simple: more than one local GPU, an integrated
   GPU, no GPU, or a model larger than every device together (so `--fit`
   can spill to CPU). A load that runs out of memory with a computed split
   is retried once without it.

### What could not be tested, and caveats

- The MacBook Air's RPC worker started resetting connections partway through
  (about 06:00 on the run day, after it dropped out of discovery once) and did
  not recover. Every cell that listed it afterwards aborted
  ("Remote RPC server crashed or returned malformed response"): the 128K
  three-device row, granite4.2's Air and three-device rows, and the auto-waterfill
  rows of the later models. The Air-inclusive rows in this section are all from
  before that.
- The Intel MacBook Pro is on another subnet and is not discovered; it was
  pinned by address, and only short prompts were run on it (a 5k prompt takes
  minutes at 13 tok/s). It would only ever be the last peer.
- Single head, single run day, one cache type for the cluster cells (q4_0),
  8K context for most cells. Load-to-load spread was not measured for every
  cell; see the paragraph under "Setup".
- The new code was validated by running the exact `tensor_split` it computes
  (pinned), not by a build of this branch discovering peers: a second instance
  on the same host cannot receive the UDP beacons the running service binds.
- The qwen3-coder rows of the older table where waterfill beat greedy were not
  rerun. A hint that they are noise: the rows quoted in #11 for one cell were 25.9 /
  60.2 / 45.8 tok/s across three repeats.

## VRAM estimate vs. measured use, November 2026

How wrong is the head-GPU memory estimate, and is the 3 GiB `fillMargin`
(`cluster/placement.go`, [#69](https://github.com/borism/ollama-cluster/pull/69))
the right size? Context: [#72](https://github.com/borism/ollama-cluster/issues/72)
(`gemma4:31b-it-qat` fits by estimate but ran out of CUDA memory on a 5k
prompt), [#73](https://github.com/borism/ollama-cluster/issues/73) and
[#81](https://github.com/borism/ollama-cluster/issues/81). Nothing here
involves a peer: it is one RTX A4500 20 GB on Linux, alone.

### Method

- A separate `ollama serve` of the installed `0.40.11-cluster.1` binary on a
  separate port, cluster mode off (no peers, no RPC workers), models read
  from the existing store (read only). It was restarted once per cache setting: `f16`,
  `q8_0`, `q4_0` with flash attention on, and `f16` with it off. The GPU was
  otherwise idle (1.6-1.8 GiB used by the desktop session and other small processes,
  recorded as "Idle" for every row).
- Nine models, every context x every cache setting (108 cells). Each cell:
  unload, read idle, load with an 8-token request (`num_ctx` set), read memory
  after the answer ("Loaded"), then one measured request of 128 tokens,
  `temperature` 0, `seed` 42, `stream: false`. `nvidia-smi` was polled every
  200 ms from the start of the load to the end of the request; "Peak" is the
  maximum over both. One sample per cell.
- Contexts: 8192 with a 40-57 token prompt, 8192 with a 4.5-5.0k token prompt
  (`prompt_eval_count` 4509-5005), and the model's maximum (`context_length`
  in `/api/show`), falling back to 65536 if the maximum did not load.
- **Estimate** is `llm.PredictServerVRAM` from this branch's base (weights file
  plus separate projector file plus KV at the cache type), computed offline
  from each model's GGUF header. The server does not log its estimate. The
  installed `0.40.11` build still has the older f16-only formula without the
  projector, so the scheduling decisions in these runs came from that one;
  the table compares the measured numbers with the current estimate.
- **llama.cpp need** is what llama-server itself projected for putting every
  layer on the GPU (`common_params_fit_impl: projected to use N MiB`, from the
  server log) plus the separate projector file. It is llama.cpp's own number,
  not a measurement.
- **Peak-idle-est** is measured peak minus idle minus estimate, filled in only
  where all weights ended up on the GPU. Positive means the estimate was too
  low. Rows with partial offload have no such number; use "llama.cpp need"
  there.
- All values are MiB. The raw per-run data, including buffer sizes parsed
  from the log, is in `docs/cluster-benchmarks-vram.csv` in the repository.

`flint:40b-a2b-q4_1`, `nemotron-3.5-lightning` and `nemotron-3.5-bolt` are
larger than the card (24, 24 and 20.5 GiB of weights, the last with a 1.6 GiB projector); they
always run with some layers or MoE expert tensors on the CPU, so their tokens
per second are not fits-in-VRAM numbers. `qwen3.6:35b-a3b-mtp` (20 GiB plus a projector) is in
the same position. "Outcome: stopped: host RAM" means the run was stopped by
the harness when the machine's free RAM fell under 1.5 GiB (the KV
cache for the CPU layers did not fit in RAM); it is not a CUDA failure. A
load that needed the fallback to the projector on the CPU is marked
"projector retried on CPU": the first llama-server start died with a CUDA
out-of-memory error while loading the projector, and the server restarted it
with the projector on the CPU. For those rows "Peak" includes the failed first
start.

### Findings

- **Outcomes.** 119 runs (108 cells plus 11 failed maximum-context attempts):
  106 ok, 6 OOM at load, 1 OOM during the prompt, 6 stopped by the host-RAM
  guard. The 6 load OOMs: `qwen3.6:35b-a3b-mtp` with `q4_0` at 8K (both
  prompt sizes, and again on an isolated rerun of both: deterministic) and
  the maximum-context attempt with flash attention off for `qwen3.6`, `flint`,
  `nemotron-3.5-lightning` and `nemotron-3.5-bolt`. The `qwen3.6` one: the fit
  projected 21019 MiB against 17907 MiB free, kept 42/42 layers with part of
  the expert tensors in host memory, and died allocating a cuBLAS workspace
  with the card at 19977 of 20470 MiB. The same model loaded with f16 and q8_0
  at 19914 and 19861 MiB, so it sits within about 0.5 GiB of the limit in all
  three; what tipped q4_0 over was not determined. The OOM during the prompt:
  `gemma4:31b-it-qat`, 262144 context, `q4_0`, flash attention on. It loaded
  with 19933 MiB used (537 MiB free) and failed on the first 54-token request.
- **#72 reproduces at load, not on the 5k prompt.** `gemma4:31b-it-qat` at 8K
  with a 5k prompt completed in all four cache settings (peaks 18833-19978
  MiB). But in 9 of its 15 runs the first llama-server start died with a CUDA
  out-of-memory error while loading the projector and the server restarted
  it with the projector on the CPU (loads were typically 70-100 s against
  29-57 s without the retry; `nemotron-3.5-bolt` did the same in all 13 runs,
  `qwen3.6` in 1). Where the
  projector stayed on the GPU (`q8_0`, 8K) the card ended with 492-506 MiB
  free and the 5k prompt added 14 MiB over the short one. So the failure
  needs the load to end within about half a GiB of the capacity, and the
  estimate does not see that: for this model it is within 165 MiB of
  llama.cpp's own full-offload need at 8K with flash attention on, and
  llama.cpp then fills the card to within about 0.5 GiB of full anyway.
- **At 8K with flash attention on, the estimate is close and 3 GiB is more
  than enough.** The gap to llama.cpp's need is under 0.8 GiB for all eight
  models that are not `gemma4:e4b`, and the one model that fits entirely
  (`qwen3.5:4b`) peaked 0.46-0.82 GiB above its estimate. Typical runtime
  extras (0.4 GiB beyond llama.cpp's buffers, 0.2 GiB for a 5k prompt) fit
  well inside 3 GiB. The estimate is too high, not too low, for
  `gemma4:e4b` (-4.5 GiB, see table).
- **3 GiB is too little when the context is large or flash attention is
  off.** Compute buffers grow with context and are much larger without flash
  attention: median 437 MiB with it and 1264 MiB without at 8K (max 4949,
  `qwen3.5:4b`), and 1884 vs 8880 MiB at the largest loaded context. The gap
  to llama.cpp's need was above 3 GiB in 8 of 8 flash-attention-off cells at
  the maximum loaded context (65536 or 262144), and in 2 of 24 with it on
  (`nemotron-3.5-lightning` at 1M context). `qwen3.5:4b` alone peaked
  +5.3 GiB above its estimate with flash attention off at 8K (a 4.5 GiB
  compute buffer instead of 0.2), and +1.9 to +2.9 GiB at 262144 context
  with it on. Quantized KV makes this worse at long context: its compute
  buffer was 2512 MiB against 1543 for f16 at 262144 (`qwen3.5:4b`). A
  margin that scales with context, and a bigger one when flash attention is
  disabled, would fit this data better than a flat 3 GiB.
- **What q8_0 and q4_0 save, in real memory.** Where the model fits, the card
  shows the whole saving: `qwen3.5:4b` at 262144 context, KV buffer 8192 /
  4352 / 2304 MiB (f16 / q8_0 / q4_0), peak above idle 13461 / 10414 / 8539
  MiB (-3047 and -4922); `gemma4:e4b` at 131072, KV 2088 / 1109 / 587 MiB,
  peak above idle 6558 / 6044 / 5522 (-514 and -1036). Where the model does
  not fit, the peak barely changes (17.0-19.9 GiB regardless) because
  llama.cpp spends the saving on more GPU layers: `granite4.2:30b` at 8K
  59 / 62 / 63 of 65 layers, 14.0 / 17.5 / 18.0 tok/s; `qwen3.8:27b`
  63 / 64 / 65 of 66, 24.5 / 25.6 / 29.9 tok/s (one short-prompt sample each).
- **Flash attention off costs memory and reach as well as speed.** At 8K
  with f16, `gemma4:31b-it-qat` got 47 instead of 50 GPU layers and 5k-prompt
  speed fell from 415 to 263 tok/s; `qwen3.8:27b` 61 instead of 63 layers
  and prompt processing of 53 instead of 144 tok/s on the short prompt. With
  flash attention off none of the seven models that overflow the card loaded
  its maximum context (four CUDA OOMs at load, three stopped by the host-RAM
  guard); 65536, the next size tried, ran for all seven. With it on, four of
  those seven loaded their maximum at all three cache types.
- **Maximum contexts that ran** (flash attention on, every cache type
  unless noted): 262144 for `qwen3.6`, `flint`, `bolt` and `qwen3.5:4b`,
  1048576 for `lightning`, 131072 for `gemma4:e4b`. `granite4.2:30b` and
  `qwen3.8:27b` ran their maximum (131072, 262144) with `q8_0` and `q4_0`;
  `gemma4:31b-it-qat` with `q8_0` only (its `q4_0` maximum OOMed, see above,
  and 65536 ran). With f16 the maximum attempt of these three was stopped by
  the host-RAM guard and 65536 ran.

### What could not be measured

- No peers: nothing here says how the margin behaves with a computed split.
  Only the two small models fit entirely, so the measured estimate error for
  20 GB-class models comes from llama.cpp's own projection, not from a
  measurement.
- One sample per cell (the `qwen3.6` `q4_0` OOM was repeated). Tokens per
  second come from a single request, 50 tokens of prompt for the short rows,
  and are noisy (`flint` short-prompt generation: 55, 34, 28 tok/s across the
  three flash-attention-on cache types, which I do not attribute to the
  cache).
- The installed build is `0.40.11-cluster.1`, older than the base of this
  branch; llama.cpp's fit and the projector fallback are from that build.
- "Maximum context" for `gemma4:31b-it-qat`, `granite4.2:30b` and
  `qwen3.8:27b` with f16 (flash attention on or off) was not reached because
  the harness stopped the run at under 1.5 GiB of free host RAM, so whether
  they would have run, slowly, is unknown. A 200 ms poll can miss a short
  allocation spike. No image requests were sent, so the projector's
  per-request memory was not exercised. One request at a time
  (`OLLAMA_NUM_PARALLEL` 1).
- `nemotron-3.5-bolt` appeared on the machine after the first f16 pass; its
  f16 flash-attention-on cells were run separately at the end with the same
  harness.

## Open questions

- **Why greedy usually beats waterfill, and the `granite4.2:30b` cliff.**
  Answered in the [placement study](#placement-study-october-2026): the KV cache
  is counted (the theory in the first version of this page was wrong), the
  difference between the strategies is whether the slowest peer holds weights,
  and the cliff is the estimate adding that peer (spuriously for a quantized
  cache, for real with f16 at 128K). What is still open is the old table's
  rows where waterfill won (`qwen3-coder:30b` at 32K and 128K): they were not
  rerun.
- **`qwen3.8:27b` cluster runs that offloaded 0/66 layers.** Rerun on the fixed
  build in the study: 66/66 layers offloaded over the A4500 and the M2 Max,
  29.8 ± 0.8 tok/s with the default split and 33.7 ± 0.9 with a fuller A4500
  (27.5-32.2 for the A4500 alone with 2 layers on the CPU). The 0/66 in the old
  rows is not reproduced on this build; its cause is unknown.
